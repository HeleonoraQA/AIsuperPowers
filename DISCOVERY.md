## 1. Intent и почему это существует

Личное CLI-приложение: человек смотрит, что есть дома, и получает 1–3 блюда, которые реально приготовить, с фильтром по способу (пар / духовка / плита). Без аккаунтов, без внешних API, без GUI.

Успех для пользователя: ввёл продукты → увидел понятное меню на русском → список сохранился в JSON. Неуспех даже при «работающем» коде: ломается схема JSON, блюда выбираются случайно, частичное совпадение подсовывается без спроса, появляются зависимости без разрешения.

## 3. Цели, не-цели, анти-цели

**Цели (MVP):** ввод продуктов, сохранение в JSON, подбор блюд (полное/частичное), меню из 1–3 позиций с категорией приготовления.

**Post-MVP:** время готовки (`cooking_time`).

**Не входит:** GUI, внешние API рецептов, авторизация, мультипользовательское облако.

**Анти-цели:** случайный выбор блюд; два написания одного продукта (`Картофель` / `картофель`); лишние поля в JSON, которые потом нельзя отличить от схемы; новые библиотеки «на всякий случай».

## 4. Ограничения

- Только локальные файлы.
- Строгая схема JSON: лишние и отсутствующие поля — ошибка.
- Новые зависимости — только с явного разрешения.
- Агент: TDD, ruff, без ломания существующего CLI.

## 5. Вопросы Discovery из `docs/plan.md`

### 5.1 Стек: Python vs Node.js

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| **A. Python 3.11+ + stdlib** (рекомендация и факт) | JSON, argparse, dataclasses из коробки; удобный pytest; совпадает с учебным стеком | упаковка в exe не проверялась |
| B. Node.js + fs | привычный JSON | `plan.md` уже Python-ориентирован после этапа 1; смена стека ломает тесты и OpenCode-правила |

**Выбор:** A. Python, pytest + ruff как dev. Git не подключался.

Пересмотреть, если понадобится веб-UI или exe (D1).

### 5.2 Структура базы рецептов

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| **A. Массив объектов с фиксированными 4 полями** (рекомендация и факт) | простая валидация, линейный поиск на 10 записях, TDD без БД | любое новое поле (время) ломает загрузчик |
| B. Свободный JSON / опциональные поля сразу | проще наращивать | два представления схемы, слабее тесты сид-данных |
| C. SQLite / индекс | запас по скорости | избыточно для 10 рецептов, новая зависимость |

**Выбор:** A. Поля: `id`, `name`, `ingredients`, `cooking_method`. Ингредиенты в файле уже канонические (нижний регистр, один пробел). `ingredients.json`: `ingredients` + `updated_at` (ISO-8601 UTC без микросекунд).

Пересмотреть на этапе 5: опциональное поле vs миграция всех рецептов (D3).

### 5.3 Алгоритм поиска и частичное совпадение

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| A. Всегда частичное, порог вроде 0.5 | больше «есть что показать» | предлагает блюда, к которым не хватает продуктов, без явного согласия |
| **B. Полное совпадение по умолчанию, частичное явным флагом** (рекомендация и факт) | честное «можно приготовить сейчас»; частичное остаётся для исследования | при бедном наборе чаще «не найдено» |
| C. Случайный выбор из подходящих | разнообразие меню | ломает TDD и воспроизводимость |

**Выбор:** B.

- `ratio = matched / len(recipe.ingredients)`
- фильтр `method` и `ratio >= min_match_ratio` (по умолчанию 1.0)
- сортировка: ratio ↓, `name`, `id`
- `limit` по умолчанию 3; пустой ввод или `limit == 0` → пустой список
- линейный перебор (D5): 10 рецептов, индекс не нужен

Пересмотреть, если UAT покажет, что частичные предложения нужны по умолчанию (D4).

### 5.4 TDD поиска без случайности

| Подход | Плюсы | Минусы |
| --- | --- | --- |
| **A. Чистая функция + фиксированные рецепты в памяти** (рекомендация и факт) | нет файлов, нет `random`, детерминированные assert по `id`/`ratio`/`missing` | CLI и диск тестируются отдельно |
| B. Тесты только через CLI и `recipes.json` | ближе к пользователю | хрупко к сид-данным, сложнее изолировать алгоритм |
| C. Мок `random` | можно оставить «случайное меню» | скрывает недетерминизм, тесты врут |

**Выбор:** A. `search` не знает о файлах и консоли. CLI подменяет `input_fn`/`output_fn` и пишет во временные пути. Сид-данные проверяет `tests/test_seed_data.py`.

## 6. Выбранное направление

Локальный Python CLI с жёсткой JSON-схемой, канонизацией ингредиентов и детерминированным поиском. Слои разделены так, чтобы алгоритм тестировался без I/O. Частичное совпадение — опция, не сюрприз. Это уже лежит в коде; Discovery подтверждает, что реализация совпадает с планом этапов 1–4.

**Вызовы, оставленные строителю (уже закрыты в коде, не в разговоре):** коды возврата 0/1/2, формат строки меню, атомарная запись через tempfile + `os.replace`, отказ неканонических строк при загрузке файлов.
